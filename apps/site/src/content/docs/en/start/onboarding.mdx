The app walks a server from its address to a working machine. Some steps only show up when they apply: the agent step when the agent is missing or behind, the backup and data steps when your organisation has backups. The rail at the top counts the steps this server will actually walk. You can go back until something is installed; after that, the way back is the way through, and an interrupted onboarding picks up where it stopped.

The app has to be [installed and linked to your account](/docs/start/install/) first, for an organisation whose licence is valid: free up to its first servers, with a licence beyond. Without it, every step holds where it is and says why.

## 1. Server

Choose a server the app already knows, or add one: its address, a port if it is not 22, and a root or sudo account for the first connection. Then the key: the app generates an ed25519 key for this server, keeps the private half on your disk, and writes the public half into the server's `authorized_keys` — with the account's password if you give it, or with a command you paste yourself. It then signs in with that key alone before going on. See [your key](/docs/start/keys/) and [connect the app](/docs/start/connect/).

## 2. Inspection

The probe reads the distribution, the architecture, the memory, the free disk and what is already installed, and gives a verdict: ready to be installed, already managed by Pupitre, already in use by other software — which Pupitre leaves alone — or incompatible, with the reasons and what would let it go on. It writes nothing.

## 3. Agent

Only when the agent is missing or behind. The app declares the server to your organisation, copies the signed agent over the open SSH session, checks what the server received against the release's checksum, and starts it. A machine that already carries its identity is not declared twice: a connection cut between the exchange and its answer is taken up again, not replayed.

## 4. Backup

Only when your organisation has backups. Start from one, or from an empty server. Starting from a backup takes the bucket connected in the app and the backup passphrase, checked on your computer before the server is asked anything; the server then takes that backup's configuration, and the next two steps open on what it held. The data itself comes back at the end. See [backups](/docs/daily/backups/).

## 5. Services

The catalogue, grouped by category. `core.system` and `core.hardening` are always included. Each module states what it installs and what it will ask you for, and presets cover the common shapes.

## 6. Configuration

Versions, ports, accounts, secrets. Every field says what it expects and refuses what does not have the right shape, at its own height, as you fill it in. A bubble beside the caption says where to find a value: the exact permissions a token needs, the page that issues it, what it costs to get it wrong. The action sits at the bottom.

A module that goes through an account of yours — Cloudflare, GitHub, 1Password, Neon, Vercel, Supabase, Stripe — asks for that account here, above its own questions. You give each token once, for every server, and the app checks which account it opens as you paste it. The token stays in your computer's keychain; what a server needs of it travels on the install's secret line, over the SSH session's standard input, and is never shown again.

Before it runs, the app asks the server to weigh the configuration: a port something already listens on, a directory that turns out to be a file, a time zone the machine does not know. What it refuses comes back on the field it belongs to.

## 7. Installation

Step by step, live: the module, the step, the counter, the duration. A configuration that would not hold is refused before the first step, machine untouched and fields named. A step that fails does not stop the other modules: it is noted, and the app offers to replay that module. Every step is idempotent, so running the install again does no damage. See [troubleshooting](/docs/account/troubleshooting/).

## 8. Security

The hardening creates the working account `dev`, copies your keys to it, checks that your key opens it, then turns passwords off, sets `AllowUsers`, starts `ufw` and `fail2ban`, and closes root **last**. If the check fails, root is not closed and the app keeps using the first account. The “Keep root access” option leaves root reachable by SSH key — never by password — and applies all the rest. The app then reconnects as `dev`.

## 9. Data

Only when the server started from a backup. Choose the parts to bring back — databases, projects, the `dev` account, extra folders — and the app restores them, then starts the projects. Or leave the data in the bucket.

## 10. Ready

The app says which account it connects with and whether root is closed. The onboarding is done and does not come back.

## After the onboarding

The app is now the window onto that machine: the dashboard, projects, terminals, agents, services. Your first project is a git URL or a folder on the machine: the agent clones it, installs its dependencies, starts it in `tmux`, and reports the port, the URL and the logs. See [projects](/docs/daily/projects/). Adding a module later is the same catalogue screen, without the rest of the walkthrough.
