Three additions on the server, and the app that goes with them.

## The gallery

- **The gallery can be published.** *Browser and gallery* takes a subdomain in Services; the exposure already installed — Cloudflare Tunnel or Caddy — then serves the gallery at `https://<subdomain>.<domain>/<token>/`. The token is drawn by the agent and kept in `/etc/pupitre/shots.env`, readable by root alone; without it every address answers 404. Whoever holds the URL opens the image — you, an agent, someone you send it to. Without a subdomain, the gallery answers on the server only, as before.
- Moving your domain takes the gallery's name with it, and keeps the token.
- **A capture is filed under its project**: the one `--project` names, else the one whose folder `shot` runs in, else the one serving the captured URL, else *Unfiled*. Files live in `~/shots/<project>/<day>/`, the URL mirrors them, and `shot` prints the public address when there is one.
- The gallery in the app has a tab per project, and a viewer that shows the capture's project, its date, the image, its path on the server and its public address — or, when there is none, what to do about it. Actual size, filmstrip and deletion are in the viewer.

## Projects

- **Every project receives its port, its addresses and the domain in `PUPITRE_*` variables**: `PUPITRE_HOST` and `PUPITRE_PORT` to listen on, `PUPITRE_URL`, `PUPITRE_LOCAL_URL` and `PUPITRE_PUBLIC_URL`, the addresses of the project's other processes and of the process's routes, `PUPITRE_DOMAIN`. A script reads them instead of hardcoding a port, and publishing a route or moving the domain changes nothing in the code.
- A process keeps what it received at start. The app marks a process running on values that have since changed, and offers to restart it.
- A terminal receives the variables of the folder it stands in, refreshed at every prompt. An agent opened on a project receives the project's, and learns they exist through the `project-env` skill.
- `PORT` and `HOST` are never set: the repository's `.env.local` keeps authority over them, and no secret travels through these variables.

## Removing Pupitre from a server

- **`pupitred uninstall` removes the agent in one command**: its services, its binary, its state, its logs and its passwordless sudo lines. The services, the databases, the projects, the `dev` account, the securing, the keys and `/etc/pupitre/env` stay where they are — the machine keeps working without Pupitre.

## Known limits

- The gallery's token is its only lock: anyone holding a published capture's URL opens it, so nothing secret belongs in a capture.
- A server that has not yet accepted the sudo password keeps the old rule, without a password, until it is applied.
- Lose every authorised device and access is put back only from the host's console, with `sudo pupitred keys reset`.
- Docker volumes are not backed up; the app says so when the Docker runtime is installed.
- Whoever can read the bucket reads the manifests, which are in clear: the server's name, the names of the projects, the databases and the folders, the address and branch of the repositories. Never a content, never a secret — those are sealed.
- Whoever holds the S3 key can erase the backups: object versioning or object lock on the bucket is the answer, and the guide says so.
- Lose the passphrase and the backups are unreadable — nobody can recover it.
- The Windows installer is still unsigned: SmartScreen warns at first launch.
