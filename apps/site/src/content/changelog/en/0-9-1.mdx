Fixes in the app; the agent does not change in this version.

## Backups

- **Changing the bucket's keys now reaches the server.** The check before **Apply** no longer weighs the agent's verdict on a bucket the app itself holds the values for: the agent was judging the bucket with the new access key and the old secret key, refusing, and **Apply** did nothing — the server kept the old secret key and every backup failed on *the secret key does not match*.
- The connection to the bucket **leaves Settings › Connections**. The **Destination** tab shows what the server holds — bucket, endpoint, key ID, fingerprint — saves a changed destination and applies it to the server at once, secret key included, puts this computer's key back on demand, and says its refusals right there.
- **Reset backups** uninstalls the backup module from the server and, by default, forgets the bucket on this computer: the setup starts again at its first step. The backups already made stay in the bucket and in the list.
- The page of a backup service sends you to the server's **Backups** page.
- A server whose backups already fail on the secret key is mended from the **Destination** tab: **Send this computer's key to the server again** when this computer holds the right keys, otherwise **Change the destination** and paste the secret key again.

## Known limits

- Docker volumes are not backed up; the app says so when the Docker runtime is installed.
- Whoever can read the bucket reads the manifests, which are in clear: the server's name, the names of the projects, the databases and the folders, the address and branch of the repositories. Never a content, never a secret — those are sealed.
- Whoever holds the S3 key can erase the backups: object versioning or object lock on the bucket is the answer, and the guide says so.
- Lose the passphrase and the backups are unreadable — nobody can recover it.
- The Windows installer is still unsigned: SmartScreen warns at first launch.
