# 0015 — `dev` uses a password for sudo, except for `pupitred`

Date: 2026-09-24 · Status: accepted

The `dev` account no longer holds `NOPASSWD:ALL`. Two rules replace it:

- **Without a password, only two exact `pupitred` lines,** by its absolute, root-owned path: `pupitred serve` and `pupitred binary install`, with no wildcard. `pupitred serve` there is a limited session, which refuses anything that configures the machine, reveals a secret or changes trust; the app opens `pupitred serve --privileged` with the password for those gestures. Placing an agent binary goes through `pupitred`, which verifies the Ed25519 signature before installing, and no longer through an `sh -c` under sudo.
- **Everything else asks for `dev`'s password.**

The password:

- **It is generated by the app, on the customer's computer.** Only its `crypt` hash goes to the server (`chpasswd -e`); the platform sees neither.
- **It is kept in the computer's keychain.** The app displays it and copies it from the server's sheet.
- **It is set by hardening** for a new server. An existing server is offered it by the app, because an agent migration cannot invent a password the customer would not know. Until they accept it, that server keeps the old rule and the app flags it.

Consequence: `pupitred` acts as root on paths that `dev` controls, and it no longer follows a link from `dev`. This is now the boundary:

- writes under `/home/dev` through the `os.Root` primitives;
- `O_NOFOLLOW`;
- reading environment templates within the project root.

Why: AI agents, `postinstall` scripts and everything that runs as `dev` work unattended. With `NOPASSWD:ALL`, each of them was root: it read the server token and the bucket keys, and could break the machine. Now, becoming root requires the customer. The customer, for their part, keeps sudo for their own use: a password to paste, as on any well-kept server.

Ruled out:
- **Keeping `NOPASSWD:ALL` and documenting it**: the risk touches precisely the use Pupitre sells, autonomous AI agents on the server.
- **Removing sudo from `dev`**: the customer must be able to administer their machine.
- **A passwordless allowlist of commands (`apt`, `systemctl`)**: each opens root through its options.
