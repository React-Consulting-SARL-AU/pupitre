# Security

## What we do not work around

The source code is public ([decision 0018](./decisions/0018-source-available-and-free.md)): **security does not rest on its secrecy**, and never has. Everything that follows holds against an attacker who has read every line of `apps/agent`, `apps/desktop` and `packages/api`. The binary is no longer obfuscated — garble is removed — and there is nothing to hide in it: no private key, no platform secret, no shared token is embedded in it; the only key it carries is the **public** half of the release key.

What protects is what a reader of the code cannot fabricate: the private keys of the customer's devices, which never leave their laptop; the private release key, which signs every binary and lives only in 1Password and the repository's secrets; the server tokens, drawn at random and stored hashed; the Worker's secrets. A customer is root on their server and can copy or recompile anything there: on their own machine, that is their right, and the licence leaves it to them. What they cannot do is make the hosted platform believe a server is licensed when it is not, or push an unsigned binary onto someone else's server. Resale, for its part, is forbidden by the licence (Commons Clause), not by technology.

## Where the secrets live

| Secret | Where | Who sees it |
| --- | --- | --- |
| A device's private SSH key | the app's data folder, `keys/device` and `keys/<server>` in 0600 | the user, on that device. Never the API, never the console, never an email. `keys/device` also signs key approvals, through `ssh-keygen -Y sign`: the message goes through standard input, the key stays on disk |
| A server's signers | `/etc/pupitre/signers.json`, 0600 root: the public keys the agent holds as trusted, and recent removals | root. They are not secrets, but they are the server's root of trust: nothing is added to it from the platform without a signature from a key already in it |
| Desktop session token (bearer) | `safeStorage`: macOS keychain, Windows DPAPI, Linux libsecret | the app |
| Enrolment token | the app's memory, once, at installation; handed to the agent by the protocol's `enroll` command, on the secret stream | the app, then the agent that exchanges it |
| Server token | `/etc/pupitre/server.token`, 0600 root; hashed in the database | the agent. Gives access only to its own server's state. Rotated at each reinstallation |
| Platform address | `/etc/pupitre/platform.url`, 0644 root | the agent. It is not a secret: it is the console this server accepted at enrolment, and the one it answers to alone |
| Stripe and R2 tokens | Wrangler secrets of the only online environment, `production` | the API. The database has no token: it is a D1 bound to the Worker, which nothing else reaches |
| Binary signing key, R2 write key, Developer ID certificate and Apple notarization key | the release's 1Password note, copied into the GitHub repository's secrets by `release secrets`; the runners of `release.yml` receive them in their environment for the duration of a release, never in a file | the release chain. GitHub is the only station that signs: a compromised repository signs a release, and that is the accepted cost of a hosted chain |
| Publication token (`PUPITRE_PUBLISH_TOKEN`) | Wrangler secret of the console's Worker, and the same value in the production and release 1Password notes | the release chain. It opens only the version routes: no customer, no organization, no server |
| The customer's secrets (database passwords, Cloudflare tokens, 1Password) | `/etc/pupitre/env`, 0600, on their server; the tokens a CLI reads from its environment (Neon, 1Password, Wrangler, Vercel, Supabase, Stripe) also in `/home/dev/.config/pupitre/env`, 0600 `dev` | them alone. They never go up |
| `dev`'s sudo password | generated on the workstation by the app, kept in the keychain (`sudo/<server>.password` in the data folder, encrypted by `safeStorage`); without a keychain — Linux on `basic_text` —, in memory for the duration of the session, shown to be noted down. On the server, only its SHA-512 `crypt` hash, in `/etc/shadow`, set by `chpasswd -e` | the customer. The hash travels on the secrets line of `harden.sudo`, never in `params`, a log or an error message; the password leaves the computer only on the first line of the standard input of a privileged session, read by `sudo -S`, or of a development agent install; the platform sees neither |
| Backup passphrase | nowhere: typed on the workstation, derived (PBKDF2-SHA256, 600,000 rounds) into an X25519 key, then forgotten | no one. Lost, it makes the backups unreadable; the app says so when having it chosen |
| Backups' private key | the app's memory for the duration of a restore, then the secrets line of `backup.restore.setup` and `backup.restore.data`; the agent uses it in memory | the agent, for the duration of the command. Never written, never logged, never in `params` |
| Backups' public key and salt | the app's `backup` connection, `install.json` (`recipient`, `kdf_salt`), each manifest, the platform | everyone: they are not secrets. The server encrypts for this key and cannot decrypt |
| S3 key of the backup bucket | the app's keychain (`backup` connection); the server's `install.json` (`core.backup`, the secret key among the secrets); the secrets line of a restore | the app and root on the server. Never the platform, never a command line, never the log |
| Configuration kept during a restore | `/var/lib/pupitre/restore/before/`, 0700 root, from `backup.restore.setup` to the end of `backup.restore.data` or to `backup.restore.abort`; the downloaded parts, encrypted, in `/var/lib/pupitre/restore/` for as long as it takes to verify then open them | root. It is the earlier `install.json`, secrets included, and nothing more readable than it was |
| Access keys for published addresses | generated on the workstation by the app and kept in the keychain (`access/<server>.json`, encrypted by `safeStorage`); the server holds only the SHA-256 hash, in `/etc/pupitre/gate/access.json` (0600 root), next to the secret that signs the `__Host-pupitre` cookie | whoever holds the key, or the cookie it set, opens the projects it names. No expiry: revocation from the app cuts everyone off at the next request. See [0017](./decisions/0017-access-gate.md) |
| What the installation received (`/etc/pupitre/install.json`) | 0600 root: the modules, their values and their secrets, so that a replay from the machine knows how to answer everything | root. An uninstall erases the module's line there — values and secrets — and each module removes from `/etc/pupitre/env` the keys it had placed there (`forget-passwords`, `forget-providers`). It is the accepted exposure of the root-is-privileged model: a root that reads this file was already reading `/etc/pupitre/env` |

## On the customer's server

- **A static Go binary**, compiled with `-trimpath`, symbols and debug tables stripped, Ed25519-signed by the release key. It is not obfuscated: its code is public. No script, no source file, no archive — not to hide, but because a readable file placed on the server is a file that root or `dev` can modify under the agent's nose.
- **A licence bound to the server.** An organization is licensed up to `FREE_SERVERS` servers with nothing else, and beyond by a live licence; an organization that exceeds its quota without a licence, or that the platform has suspended, returns `suspended` and enrolment is refused. At installation, the agent receives an enrolment token signed by the platform for this device and this account; it exchanges it for a server token. It reads `/agent/state` every 30 seconds; each successful read renews a licence valid for 24 hours, cached in `/var/lib/pupitre/license.json`. Without a successful read for 7 days, it goes into **restricted mode**: what is running keeps running, and only `hello`, `ping`, `snapshot`, `status`, `diag`, `agent.upgrade`, `agent.migrate`, `enroll` and `platform.sync` answer, as the protocol fixes it (`RESTRICTED_COMMANDS` in `packages/shared`). `enroll` is among them because it is the gesture that repairs a server whose token was lost or revoked, and because the enrolment token comes from the platform, for an authenticated account and a licensed organization. A binary copied elsewhere has no token for the hosted platform; recompiled without the verification, it only fools its own owner, and obtains from the platform neither device keys nor a signed version.
- **The modules run only with a valid licence**, and some of their steps depend on parameters received from the platform at enrolment (versions, download URLs, apt repository keys), not only on what the binary contains.
- **An apt repository key is placed only if it is the one the publisher publishes.** The binary pins the fingerprint of each key it fetches (`internal/sys/apt/keys.go`); a key that carries another, or one more, is erased before apt reads it, and an address without a fingerprint is refused. A publisher who rotates its key requires a new agent version. An archive with no published fingerprint (the Cursor CLI) is never extracted by root: `dev` unpacks it, from standard input.
- **No secret on a command line**, where `ps` would read it: `mongodump` and `mongorestore` receive their credentials through a 0600 configuration file, `redis-cli` its password through `REDISCLI_AUTH`, the other engines theirs through standard input.
- **Backups leave the server encrypted.** Each part is sealed on the server for the customer's public key (X25519, block-wise AES-256-GCM) before reaching its bucket: an exposed bucket or a leaked S3 key yields only opaque bytes. The platform receives only an address, sizes, counts and the manifest fingerprint; the agent refuses to restore a part whose fingerprint differs from the one the recorded manifest gives it. The manifest, for its part, is in clear in the bucket — names of the server, projects, databases, folders, repository addresses and branches — and the guide says so. The bucket is reached only over HTTPS: the app, the agent and the platform refuse an `http://` endpoint, on which request signatures would pass in clear. See [backups.md](./contracts/backups.md).
- **A published address answers only to an access key**, except for a process the customer has declared public. Each name goes through `pupitre-gate` (`127.0.0.1:8098`):
  - the gate runs as root with no capability (`CapabilityBoundingSet=` empty, `NoNewPrivileges`);
  - on a read-only system, and `/etc/pupitre` shows only `gate/` there;
  - a compromised gate therefore reads neither `/etc/pupitre/env`, nor `install.json`, nor the server's token.
  - It strips the key, the parameter and its cookie before forwarding, and replaces any incoming `Pupitre-Identity`.
  - Only the privileged session creates or revokes a key, and opens a project to the web: an AI agent as `dev` does not lift the protection.
- **The screenshot gallery listens only on the loopback** (`127.0.0.1:8099`, read-only) and travels over the protocol, in the app's SSH session. Nothing publishes it by default: it has an address on the web only if the customer gives it a subdomain in the `ai.browser` service, and it then goes through the exposure they installed, like a project. This address has no login but a 128-bit token as the first segment of each path, generated by the agent, kept in `/etc/pupitre/shots.env` (0600 root, handed to the service by systemd, never on a command line); without it, everything is a 404, the list included. Whoever holds a capture URL holds the entire gallery: emptying the subdomain forgets the token and cuts all the addresses given.
- **Controlled distribution**: the binary is not public — the app's artifacts are, on `dl.pupitre.studio`, but the agent stays in a private bucket. The app downloads it from the platform with the device's token, verifies its signature (Ed25519, public key embedded in the app), and pushes it itself to the server over SSH; on a server reached as `dev`, it is `pupitred` that verifies the signature again before replacing itself.
- **What remains the customer's, unconditionally**: their projects, their databases, their secrets, tmux, the installed services. In restricted mode, they have lost only Pupitre.

### What `dev` can do, and what it no longer can

Everything that runs as `dev` — coding agents, `postinstall` scripts, a terminal — runs unattended. Since [decision 0015](./decisions/0015-sudo-by-password.md), none of it becomes root without the customer:

- **`dev` has a sudo password**, which the app generates at hardening and keeps in the keychain. `sudo` asks for it for everything, except for two exact lines: `/usr/local/bin/pupitred serve` and `/usr/local/bin/pupitred binary install`. A command that sudoers writes with arguments matches only those arguments; the rule carries no wildcard, which would also match a space. `pupitred serve --privileged`, `keys reset`, `uninstall`, `migrate`, `install`, `dev`, `version` — any other line — ask for the password, and since `SETENV` is not granted, neither `sudo VAR=… pupitred serve` nor `sudo -E` goes through.
- **`pupitred serve` is a limited session.** It is the line that everything running as `dev` can open; it answers only commands whose worst case, in `dev`'s hands, is a nuisance: reads that return no secret root holds, `dev`'s work on its own projects, files and processes, an already configured unit started or stopped, a signed agent above the floor. What configures the machine, reveals a secret, imports a dump, touches backups beyond their state, changes whom the server trusts or which platform it answers to, restarts or downgrades the agent is refused with `privilege_required` and belongs only to `pupitred serve --privileged`, which sudo launches only on the password. The list is `LIMITED_COMMANDS` in `packages/shared`, an allowlist; the command-by-command table is in [the protocol](./contracts/agent-protocol.md#two-sessions-passwordless-and-privileged).
- **The app opens the privileged session on demand**, with the password it keeps, written on the first line of the SSH session's standard input and read by `sudo -S` — never an argument, never an environment variable, never a log — and closes it after a minute without use. A refused password shows at sudo's second prompt: the app cuts off and says so, without retrying. A computer that does not hold the password makes no privileged gesture until it has been entered — rerunning hardening is one. `pupitred dev`, typed as `dev`, goes likewise through the limited session, and asks for the password on the terminal for its privileged verbs.
- **`pupitred` cannot be replaced by `dev`**: `harden.sudo` refuses to set the rule as long as the binary, or a folder above it, belongs to anyone other than root, is a link, or is writable by the group or others.
- **A new agent binary goes only through `pupitred binary install`**, which verifies the Ed25519 signature with the key it carries and the version floor before replacing itself. The version and the signature arrive on the first line of standard input, not as arguments: the passwordless line stays exact. `--allow-downgrade` and `--privileged` make another line, which asks for the password; an agent built without a release key — the development agent — has nothing to verify the bytes with and places a binary only through `--privileged`. No more `sh -c` under sudo. Only the first installation, as root on a bare server, writes the binary that the app verified itself.
- **A password does not open SSH**: `harden.sudo` refuses as long as `sshd -T` accepts a password for `dev`.
- **A server installed before** keeps `NOPASSWD:ALL` until the customer accepts a password — the agent cannot invent one that it would not know. `snapshot` says so (`machine.sudo: "nopasswd_all"`), and the app offers to rerun hardening.
- **`pupitred`, as root, no longer follows a link from `dev`.** This is now the boundary. Writes under `/home/dev` go through `os.Root` primitives and a path resolved step by step, which follows a link only if root holds it together with its folder (`internal/sys/trusted.go`); an appended file is opened with `O_NOFOLLOW`/`O_EXCL`; a `chown` is an `lchown`; environment templates (`.env.example`, the 1Password template, `op.config.json`) are read inside the project root; database dumps are written to `~/dumps` from the tool's output, never through a path it would follow; a restore works inside the account's root; a process is signalled through a pidfd, after checking its owner, never by a PID that someone else could have taken over.
- **Kernel links are protected by hardening**: `fs.protected_hardlinks=1` and `fs.protected_symlinks=1`, in `/etc/sysctl.d/60-pupitre-links.conf`, applied immediately and at every boot. A hard link placed by `dev` is an ordinary file, and the first setting is what prevents `dev` from placing one to a file it does not own.
- **What remains**: a server under the earlier rule (`nopasswd_all`) stays root for everything that runs as `dev` until its customer has accepted a password; and `pupitred` reads its paths from the environment (`PUPITRE_*_PATH`), so a sudoers that the customer had set to `!env_reset` or with `SETENV` would reopen the door.

## In the desktop app

- Main process compiled to V8 bytecode (electron-vite's bytecode plugin): a loading choice, not a protection — the code is public; what protects the installed app is the integrity of its archive and its signature. The preload stays JavaScript — Electron loads it in the renderer, whose V8 rejects the cache produced by the Node isolate — and it declares only channel names. An asar archive whose integrity is verified by a fuse, loading restricted to the archive, signing and notarization.
- The renderer stays minified JavaScript: it contains only interface.
- The account is required: the app requires a first successful connection, then checks the licence at each launch, with the same seven-day grace. Only a development build carries a licence of its own, a mirror of the agent's `dev` tag.
- The renderer has no access to the system. No free string coming from the interface reaches a shell: the renderer names a project and an action, the main validates the name against the list the agent has just given.

## Between the app and the server

- SSH with the customer's key, `IdentitiesOnly yes`, host key pinned from enrolment: the agent sends the host key's fingerprint to the platform, the app compares it with what `ssh` sees, a mismatch blocks and explains itself.
- Hardening closes root and passwords **after** verifying that a key opens `dev`. If the verification fails, root stays open and the app says so.
- A `keep_root` option for whoever wants to keep control of their server: root stays reachable by key, never by password, and all the rest of the hardening applies. The app says this too, and does not confuse it with a hardening that gave up.
- An SSH option on 443 in addition to 22 for networks that filter.

## Between the server and the platform

- Outbound HTTPS only. The agent polls `/api/v1/agent/state` every 30 seconds (device keys and their approvals, target version, licence) and sends a heartbeat every 5 minutes.
- Device keys go in a marked block of `/home/dev/.ssh/authorized_keys`, written atomically, without touching lines outside the block. A removal takes effect in under a minute.
- The platform cannot execute a command on a server. The day something has to be "done", it is a reinstallation by the customer from the app.

### What the platform can do, and what it no longer can

Since [decision 0014](./decisions/0014-keys-approved-by-a-device.md), a compromised platform, a stolen admin session or an XSS in the console no longer give access to customers' servers.

- **It cannot open a server.** It relays devices' public keys and approvals, but the agent places a key only if it is already a signer, or if it arrives with an SSHSIG signature from a signer (`pupitre-key-approval`) that covers this server, this key, this user and a date less than seven days old. The platform has no device private key: it cannot fabricate an approval. It checks the form of what it receives and who has the right to approve, never the signature as a trust decision — that is the agent's business.
- **The root of trust is placed by SSH.** At onboarding, the app places its device's key through `keys.trust`, on its own session. Servers already in service had their keys of the moment become signers once, at migration 6. `sudo pupitred keys reset` does it from the host's console when all devices are lost.
- **It cannot redirect an approval.** The server identifier the agent compares is the one it recorded at its enrolment, and which the platform can no longer change; an approval older than the last removal of a key is refused.
- **It can cut an access, never the last one.** Removing a key does not require a signature: it is the direction that closes. But the agent never removes the last key from the block: when the requested list would leave none, nothing goes out, neither on a token revocation nor on a suspension. What was cut is repaired from the host.
- **The rest of what it pushes is bounded by the agent**: the licence only restricts; the target version is an Ed25519-signed binary above a floor; a restore requires the manifest fingerprint; the server identifier follows the contract's pattern; key options are refused.
- **Adding a device to the account** requires a sign-in less than ten minutes old — passkey or second factor included when the account has one — and sends an email. Repairing a server is reserved to the assigned person or an organization admin, and rewrites neither the SSH account nor the host fingerprint; the exchange of the enrolment token requires the pinned host key.

## Platform

- Better Auth: `Secure`, `HttpOnly`, `SameSite=Lax` cookies; bearer for the app; attempt limiting; 60-day sessions renewed daily; `admin` reserved to the `platform_admin` role.
- **Rate-limit budgets are shared**: the API and the authentication routes count their windows in a Durable Object (`RATE_LIMIT`, eight instances), not in an isolate's memory — a budget holds everywhere at once. A console without the object falls back to per-isolate counting, and says so in its logs.
- **Security headers on everything the Worker answers**: CSP with no inline script other than those the console signs with a nonce drawn on each request, fonts served by the console itself, `frame-ancestors 'none'`, HSTS in production; static files carry the same prohibitions from the asset layer (`_headers`), each what suits it.
- **Origin checked**: a cookie-authenticated `/api/v1` write, and the inbox socket, refuse an `Origin` that is neither their own nor one of `PUPITRE_ORIGINS` — `SameSite=Lax` lets the cookie through from any subdomain of `pupitre.studio`. A request carrying a token is not concerned. Removing a platform team member closes their open sockets.
- Passkeys (WebAuthn) and second factor (TOTP): a passkey signs in without a magic link; the second factor, if enabled, is required after the magic link and after social sign-in, **never after a passkey**, which already proves the device and the person. Recovery codes are encrypted in the database and each serves only once. This is verified by tests.
- The second-factor challenge destroys the session opened by the magic link before answering: no bearer token goes out until the code is given.
- Stripe webhooks verified by signature, idempotent by event identifier, replayable.
- Audit of every admin action: actor, action, target, date.
- **The keys requested for a server derive from the member assigned to it, and from their membership.** Removing someone from the organization removes their keys from all servers, without an administrator having to think of it, except where theirs would be the last in the block. This is verified by a test. A new key enters only approved by a device already a signer of the server: the assigned person for their own devices, an owner or an admin for a member's.
- Automatic suspension of a server on an abuse report: licence suspended, email to the organization's owner. The platform stops requesting keys for that server, but the agent never empties the block: the keys in place stay there.
- **No error leaves the platform**: the Worker's exceptions stay in the account's Cloudflare logs, no third-party observability service is plugged in.
- The `/status` page answers without a session and exposes only aggregates: no server identifier, no email, no organization name.
- Dependencies: `govulncheck` runs in the agent's lint, in CI as at pre-push, and blocks on a reachable vulnerability; gitleaks rereads new commits in CI. npm dependencies have no automatic alert — neither Dependabot nor an audit in CI —: `bun audit` is run by hand before an upgrade. Better Auth is updated within the day of a published flaw.

## Contract

- The source is public under Apache 2.0 with the Commons Clause ([decision 0018](./decisions/0018-source-available-and-free.md)): anyone may read, build and self-host it; selling it, or a service whose value derives substantially from it, is forbidden. Security relies on the design, never on the secrecy of the code. Vulnerabilities are reported privately, as [`SECURITY.md`](../SECURITY.md) describes.
- Terms, acceptable use policy, DPA for European customers, privacy policy. The platform stores no code, no secrets, no content from the customer's server.
