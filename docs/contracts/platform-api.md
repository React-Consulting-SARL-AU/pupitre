# Platform API

Elysia, mounted on `/api/v1` in `packages/api/src/server.ts`. Three consumers: the console (session cookie), the desktop app (bearer), the agent (server token). The console consumes the API through the typed Eden Treaty client of `@pupitre/api/client`; the desktop app, through its own `fetch` client (`apps/desktop/src/main/platform-client.ts`). Better Auth is mounted separately on `/api/auth/*` by `packages/auth`.

## Authentication

| Consumer | Mechanism | Better Auth plugin |
| --- | --- | --- |
| Console | session cookie | `tanstackStartCookies` |
| Desktop app | `Authorization: Bearer <session token>` obtained through the device flow | `deviceAuthorization`, `bearer` |
| Agent | `Authorization: Bearer <server token>` | none: its own token, hashed in the database, verified by the `requireServer` guard |
| Support | session of a member of the Pupitre organization | `organization` |
| Console, without magic link | WebAuthn passkey | `passkey` |
| Console, second factor | TOTP code or recovery code | `twoFactor` |

A cookie-authenticated write (anything but `GET`, `HEAD` and `OPTIONS`) whose `Origin` header is neither that of the request, nor the console, the site or the development tunnel from `PUPITRE_ORIGINS`, nor a local origin towards a local address, receives 403 `forbidden` before any route (`packages/api/src/lib/api/origin.ts`); a request without `Origin` is not a browser page and passes. `SameSite=Lax` does not cover subdomains of the same site; a token request — desktop app, agent — is not concerned. The inbox socket checks the same rule.

Confirming a device code (`POST /api/auth/device/approve`) requires a browser session opened less than `FRESH_SIGN_IN_SECONDS` (ten minutes) ago: otherwise 403 `SESSION_NOT_FRESH` (`freshDeviceApproval`, `packages/auth/src/fresh-device-approval.ts`), and the code page sends the user back to sign-in then returns to the same code. A stolen session, an XSS in the console, are therefore not enough to bring an app session into being.

Better Auth's `admin` plugin serves only to keep `role` and the ban at sign-in: `platform_admin` has no permission there, and `adminLockdown` (`packages/auth/src/admin-lockdown.ts`) refuses any `/api/auth/admin/*` with 403 `ADMIN_ENDPOINTS_CLOSED` — no impersonation, no password, no address changed outside the platform's logged `/admin/**` routes.

Deleting one's own account goes through Better Auth (`POST /api/auth/delete-user`); the platform hooks its own in before the row goes (`configureAccountHooks`, `deleteOwnAccount`): 409 `SOLE_OWNER` with `message` and `fix` in the request's language when an organization would be left with nobody — the same guard as `DELETE /admin/users/:id` —, otherwise the assigned servers lose their assignment and `purgeUser` erases the account on the spot, along with the organizations of which it was the last member.

Elysia guards in `packages/api/src/lib/api/plugins/`: `authPlugin` (resolves session, user, active organization, role, role in the Pupitre organization), `requireOrg`, `requireRole("admin")`, `requireLicense`, `requireServer`, `requirePlatformAdmin`, `requirePlatformRole("admin")`, `requirePublisher`.

**Who opens `/admin/**`**: membership of the Pupitre organization, and nothing else. `PLATFORM_ORGANIZATION_ID` of `@pupitre/shared/platform` names this organization; the role held there — `owner`, `admin` or `member` — is handed out from its members page, as for any organization, and `authPlugin` resolves it into `platformRole`. Two guards follow:

- `requirePlatformAdmin`: **read**. Any member of the Pupitre organization passes. It refuses with 401 `unauthenticated` without a session, and with 403 `forbidden` (message `platform_admin_required`) for an account that is not a member.
- `requirePlatformRole("admin")`: **act**. Only `owner` and `admin` pass; a `member` is refused with 403 `forbidden` with the message `platform_role_required`, which names the role that is needed. This guard protects every route that writes: suspending or restoring a server, banning or unbanning an account, creating or deactivating an affiliate link. `requirePublisher` requires the same rank for a session, in addition to the publication token.

`GET /me` returns `platform_role`: the caller's role in the Pupitre organization, or `null`, and `platform_can_act`: `true` when that role passes `requirePlatformRole("admin")`, computed by the same rule as the guard (`actsOnPlatform`). The console shows the administration according to `platform_role` and greys out what cannot be actioned according to `platform_can_act`, deriving nothing from the role; it decides nothing — the guards decide.

`requireLicense` composes after `requireOrg` and requires a valid or grace licence (`licenseRefusalFor`, `packages/api/src/lib/billing/license.ts`): it refuses with 403 `license_required` when the organization holds more servers than `FREE_SERVERS` without a living licence, and `server_suspended` when its licence is suspended, with a `fix` that says: free up to three servers, a licence beyond that, `support@pupitre.studio`. It guards `POST /servers/enroll` and the assignment routes. An organization that fits within the free servers passes without a subscription of any kind.

**Data consent.** The platform's data is stored and processed by Cloudflare in the United States, so every account agrees to that transfer, dated and tied to the version of the text, before using Pupitre. `DATA_CONSENT_VERSION` (`@pupitre/shared/legal`) names the current text; `user.dataConsentVersion` and `user.dataConsentAt` (migration `0019_data_consent`, declared in `packages/auth` as `DATA_CONSENT_FIELDS`) record the last agreement. Every human guard — `requireAuth`, `requireOrg`, `requireRole`, `requireLicense`, `requirePlatformAdmin`, `requirePlatformRole`, `requirePublisher` with a session — refuses with 403 `consent_required` until the stored version is the current one, after the 401 and the account refusals: the `message` says the data goes to Cloudflare in the United States, the `fix` names `<console>/auth/consent` (`appUrlFromEnv`), in the request's language. A changed text asks every account again. Left open, through `requireSession`: `GET /me` and `PATCH /me` (the console reads the account and switches its language on the consent page), `POST /me/consent` and `POST /me/consent/decline`. Outside the guard by nature: the public routes (`/health`, `/status`, the releases' public reads, the affiliate counter), the routes of a server token (`/agent/*` — a server is not a person), `POST /agent/exchange`, the Stripe webhook, and Better Auth's `/api/auth/*` — sign-out and `POST /api/auth/delete-user`, through which an account withdraws its consent. The inbox socket refuses the same way. The console sends a session without a current consent to `/auth/consent?callbackURL=…` from the dashboard gate and the device-confirmation page, except `/dashboard/settings`, which carries the account deletion; the sign-in page states the transfer before the email field. The desktop app shows `consent_required` with its own sentence and the console's consent page (`refusal.account.consent`).

The sign-in address is changed from the console settings, through `POST /api/auth/change-email`: Better Auth sends the confirmation link to the **current** address, never to the new one, and the switch happens only once that link is opened. The template is `email_change`.

A registered passkey opens the session on its own: the relying party is the registrable domain of `BETTER_AUTH_URL` (`pupitre.studio` in production, `localhost` in development) and the trusted origins are those of the console. The second factor, when enabled, is required after the magic link and after social sign-in, never after a passkey, which is already a second factor: the verification redirects to `/auth/two-factor`, where a TOTP code or one of the ten recovery codes — single use — opens the session. The desktop app goes through the device flow and carries neither of these two plugins.

## Routes

### Me

| Method | Route | Body | Response |
| --- | --- | --- | --- |
| GET | `/me` | — | `{ user, organizations[], active_organization, role, platform_role, platform_can_act, license, servers, license_grant, data_consent, entitlement, subscription }`. `user.locale` is `fr` or `en`. `organizations[]` carries `{ id, name, slug, state, role }` and `active_organization` carries `{ id, name, slug, state, reason }`: `state` is the organization's state — `active`, `suspended`, `closed` or `deleting`, priority `deleting > closed > suspended > active` — and `reason` the reason the platform wrote when setting that state, `null` on an active organization. The dashboard shows the matching banner and offers to open another organization; a `closed` or `deleting` organization refuses `requireOrg` (403 `forbidden`, message `organization_closed`), a `suspended` organization lets in and returns `license: "suspended"` whatever its licence. `platform_role` is the caller's role in the Pupitre organization (`owner`, `admin`, `member`) or `null`: the console uses it to show or hide its administration entry. `platform_can_act` says whether this role passes `requirePlatformRole("admin")` — `true` for `owner` and `admin`, `false` for `member` and outside the Pupitre organization —: the console uses it to grey out what cannot be actioned, never to decide anything — the guards decide. `license` is `none` without an active organization, otherwise the organization's licence (`licenseForOrganization`): the platform organization is always `valid`; an organization suspended, closed or being deleted by the platform is `suspended`; otherwise, the licence that counts is the living subscription — `active`, `trialing` or `past_due`, the last touched among them, `granted` or Stripe product —, and, failing that, the last touched at all: an old subscription that still receives events does not speak for the new one. `active` and `trialing` return `valid`; `past_due` and `unpaid` return `grace`, with as horizon the date that the organization's servers have carried since the day the grace opened — the same as `/agent/state`. **Without a living subscription**, an organization whose seat-occupying servers fit within `FREE_SERVERS` is `valid`: this is the free tier, with no row in the database; beyond that — a granted licence that has expired, for example —, it goes into `grace` for `GRACE_PERIOD` then `suspended`. `servers` is `{ used, limit }` for the active organization, `null` without one: `limit` is the seat quota (`seatQuotaFor`, the one that refuses enrolment), `FREE_SERVERS` plus the seats of the living licence, `used` the number of servers that occupy a seat (`enrolling`, `active`, `grace`, `suspended`). `license_grant` is `{ status, seats, current_period_end }` when the organization holds a living licence, `null` otherwise: `seats` the seats it adds to the free servers. No offer and no price appears there. `data_consent` is `{ version, accepted_at }` (`DataConsentSchema`) when the account agreed to the current `DATA_CONSENT_VERSION`, `null` before that and whenever the stored version is an older one: the console sends the person to `/auth/consent` while it is `null`. **Legacy fields**: `entitlement` repeats `license` and `subscription` is always `null`, for apps earlier than 2.0.0 that still read them; they are removed with the next protocol generation. The types live in `@pupitre/shared/plans` (`MeServersSchema`, `MeLicenseGrantSchema`), the whole response in `@pupitre/shared/platform-api/account` (`MeSchema`) |
| PATCH | `/me` | `{ locale?, organization_id? }` | the same body as `GET /me`. What the caller omits does not move. The saved language decides that of the emails, including those a scheduled task sends without an `Accept-Language` header to read. `organization_id` must name an organization the caller is a member of, otherwise `forbidden` (403) without saying whether it exists; the switch touches only the session that asks for it — the console open alongside keeps its own — and the response immediately carries the new role and the matching licence |
| POST | `/me/consent` | `DataConsentRequestSchema`: `{ version }` | `{ data: DataConsent }`: `{ version, accepted_at }`. Records the current version and the instant, and writes `user.data_consented` to the journal (payload `{ version }`). A version other than `DATA_CONSENT_VERSION` — a page opened before the text changed — is refused with 409 `conflict` (message `consent_version_outdated`, `fix`: reload the page). Open without a consent (`requireSession`); 401 without a session |
| POST | `/me/consent/decline` | — | 204: the account is erased on the spot — user, sessions, sign-in accounts and the personal organization the sign-up created (`purgeUser`, journal `user.purged`). Only when the account has **never** agreed and holds nothing beyond its sign-up: no device, and no organization with another member, a server of any status or a subscription; the platform organization always counts as something. Otherwise 409 `conflict` (message `consent_decline_held`) with a `fix` that names `<console>/dashboard/settings`, where the ordinary account deletion says what still holds it back. The console asks for a confirmation, signs out and lands on the sign-in page. Open without a consent; 401 without a session |
| GET | `/me/devices` | — | `{ data: Device[] }` |
| POST | `/me/devices` | `{ name, public_key }` | `{ data: Device }`. The key is offered to every server the user can open, where it waits for the approval of a device that is already a signer. Requires a sign-in less than `FRESH_SIGN_IN_SECONDS` old (ten minutes, `@pupitre/shared/keys`): a session is born only from the whole sign-in, passkey or second factor included, and its age is that of this proof; otherwise 403 `reauthentication_required`, with a `fix` that says to sign in again. A `device_added` email goes to the account |
| GET | `/me/key-approvals` | — | `{ data: PendingKeyApproval[] }` (`@pupitre/shared/keys`): `{ server: { id, name }, device: { id, name, fingerprint, public_key }, user: { id, name, email }, signers[], reported_at }`, across all the caller's organizations. A server appears there for each fingerprint its last heartbeat reports as pending (`Server.keyReport.pending`) and that belongs to a device this server must carry, when the caller can approve it — they are the assigned person and the device is theirs, or they are `owner` or `admin` of the organization — **and** at least one of their devices is a signer of this server (`keyReport.signers`): these are the ones `signers` names. The app displays only the rows where its own device appears |
| POST | `/me/key-approvals` | `KeyApprovalSubmission`: `{ server_id, device_id, public_key, user_id, issued_at, signer, signature }` | 201 `{ data: { server_id, device_id, signer, issued_at } }`. Kept per `(server, device, signer)` and relayed in `/agent/state`. The platform does not judge the signature — the agent decides —, but refuses what is malformed or outside the caller's rights: 404 `not_found` when the server or the device is not visible to the caller; 403 `forbidden` when the caller cannot approve this device on this server (same rule as the list); 422 `key_approval_invalid`, with the `fix`, when the body leaves the schema, when `server_id`, `public_key` or `user_id` are not those of the server, the device and its owner, when the device is not one of those the server must carry, when `signer` is not the fingerprint of one of the caller's devices, when `issued_at` leaves the window (seven days before, five minutes after), or when the SSHSIG envelope cannot be read, does not carry the `pupitre-key-approval` namespace, a `sha512`/`sha256` hash or the key of `signer`. The log keeps `key.approved`, without the signature |
| DELETE | `/me/devices/:id` | — | 204. Removed from each server at its next successful poll of `/agent/state`, within a minute when it answers |
| GET | `/me/servers` | — | `{ data: ServerForUser[] }`: host, port, user, host fingerprint, status, `key_ready`, and `organization` — the identifier and name of the organization that holds the server, so that a member of several knows where each machine assigned to them comes from. Nothing else of the organization leaves: no role, no subscription, no seat counter. A `revoked` server never appears there: it opens nothing any more. `key_ready` is read server by server, never by account: it is `true` when the assigned member still belongs to the server's organization and keeps at least one device that **this** server has not revoked — exactly the keys the agent will receive. A device revoked on one machine leaves the others ready |

### Public status

| Method | Route | Body | Response |
| --- | --- | --- | --- |
| GET | `/status` | — | `{ data: { api, database, latest_release, active_servers, last_observation_at, freshness, checked_at, social_providers, billing } }`. No guard: the route answers without a session. `api` and `database` are `ok` or `down`, `latest_release` is the latest version published on the `stable` channel (`{ version, channel, published_at }`) or `null`, `active_servers` is the total number of servers with `active` status. `checked_at` is the instant of the computation, `last_observation_at` the date of the most recent heartbeat received from the whole fleet, or `null` if the platform has none, and `freshness` the platform's verdict on that date, against its own clock: `fresh`, `stale` beyond `STATUS_STALE_AFTER_MS` (fifteen minutes, `@pupitre/shared/status`), `unknown` without an observation. `stale` or `unknown` data forbids showing a reassuring state. Nothing else leaves: no identifier, no organization name, no machine name, no address; `last_observation_at` is an aggregated maximum, it designates no server. `social_providers` lists the social sign-in providers the platform has actually mounted (`github`, `google`, in that order), deduced from the Better Auth configuration: a provider whose identifier or secret is missing does not appear there. The list carries only names, never an identifier or a secret; the sign-in page displays only these providers. `billing` is `{ mode }`: `stripe` or `off` (`BILLING_MODE`); the console reads from it whether a payment can open. The route does not fall over for anything: a database that does not answer returns `database: "down"` and the rest empty, and an unreadable `BILLING_MODE` degrades `billing` to `{ mode: "off" }` with a log line, instead of returning 500 on the public status page |

### Servers

| Method | Route | Body | Response |
| --- | --- | --- | --- |
| POST | `/servers/enroll` | `{ device_id, host, port?, ssh_user?, fingerprint?, probe }` | `{ server_id, enrollment_token, release: { version, url, sha256, signature, channel } }`. `release` is the latest `stable` version for the probed architecture, or the latest `beta` if no `stable` exists — `channel` says which. The server is born `enrolling`, assigned to the caller; the enrolment token is valid for one hour and is stored only hashed. Refused when the organization's licence is missing (`license_required`, 403) or suspended (`server_suspended`, 403), even before counting seats. The host is normalised — lowercase, without surrounding spaces — before any read: `VPS.test` and `vps.test` are the same machine. Each device then writes the host and the account into its SSH configuration: the normalised host must be a DNS name, an IPv4 or a bare IPv6 (`isSshHost`), `ssh_user` a POSIX account name (`isSshUser`), `fingerprint` a `SHA256:` fingerprint (`isSshFingerprint`), all from `@pupitre/shared/ssh`; otherwise `validation` (422), before any read and without writing anything. An enrolment that finds a server already known to the organization — same host, same port, and a status that consumes a seat, **whichever device** enrols it — updates it, notes the device that has just repaired it and gives it a fresh token, **without consuming a seat**: this is the repair gesture for a restricted server, and a person's second computer does not make a second row of it. Its status and its server token do not move for all that: the machine keeps the access it has until the exchange gives it another, and a binary upload that fails in between leaves neither a dead token nor a row stuck in `enrolling`. The quota therefore refuses only the unknown host (`seat_quota_reached`, 403, whose message says: free up to three servers, a licence beyond that, `support@pupitre.studio`). The quota is `FREE_SERVERS` plus the quantity of the organization's `active`, `trialing` or `past_due` subscription — `granted` or Stripe product —, and nothing else; the platform organization has `PLATFORM_ORGANIZATION_SEATS`. Repairing is reserved to the person assigned to the server and to the `owner`s and `admin`s of the organization (`server_repair_forbidden`, 403), and never rewrites `sshUser` or `hostFingerprint`. `fingerprint` is the Ed25519 fingerprint of the host key, the one the agent will declare at the exchange; the app omits it when its `known_hosts` holds none, and the exchange then pins it |
| GET | `/servers` | — | `{ data: Server[] }` of the active organization — a `member` sees only the servers assigned to them, `admin` and `owner` see them all. `stale` is computed: no heartbeat for 24 h. It changes neither the status nor the licence. `usage` carries the latest sample received (`at`, `disk`, `ram`, `load` and the quantities), kept apart in `Server.lastUsage` by the heartbeat so that the list never reads the seven-day window, or `null` |
| GET | `/servers/:id` | — | `{ data: Server }` with `metrics` for the last 7 days and `events`. `not_found` (404) for a `member` to whom this server is not assigned |
| POST | `/servers/:id/assign` | `{ user_id }` or `{ invite_email }` | `{ data: Server }`. `admin` role, and a valid or grace licence (`requireLicense`). `user_id` must be a member of the organization, otherwise `not_found` (404) with a `fix`. An `invite_email` that is already a member assigns directly; otherwise the invitation goes out and the server carries `pending_assignment_email` until acceptance, which assigns it and pushes its keys |
| POST | `/servers/:id/unassign` | — | `{ data: Server }`. Keys removed, pending assignment erased |
| POST | `/servers/:id/revoke-device` | `{ device_id }` | 204. This device no longer receives this server; the person's other devices remain |
| DELETE | `/servers/:id` | — | 204. `admin` role. In two steps: on an active server, it goes `revoked`, the assignment and the keys drop immediately and `DecommissionServer` is scheduled in seven days; on a server that is **already `revoked`**, the row is erased on the spot, with its alerts and its device revocations. A second call never pushes the deadline back. `not_found` (404) when there is no row left |

### Agent

| Method | Route | Body | Response |
| --- | --- | --- | --- |
| POST | `/agent/exchange` | `{ enrollment_token, host_public_key, agent_version, arch }` | `{ server_token }`. The enrolment token is burned — its expiry falls under the same conditional write, so two concurrent exchanges make only one and the second is refused with 409 `enrollment_used`. The server takes its new token, the one it carried before is no longer valid, and its status follows the organization's licence: `active` with a twenty-four-hour window when it is valid; otherwise a `grace` or `suspended` server keeps its status and its date, and a server born during a grace period opens in `grace` with seven days. Repairing and re-exchanging never reactivates what non-payment has restricted. A server that already has a host fingerprint requires `host_public_key` to match it, otherwise 409 `host_key_mismatch` without burning the token — a reinstalled machine is removed from the console and added again; only an absent fingerprint is filled in by the exchange |
| GET | `/agent/state` | — | `{ license: "valid" \| "grace" \| "suspended", entitlement, valid_until, authorized_keys[], keys[], target_version, minimum_version, hostname, server_id }`. `license` is the server's licence; `entitlement` repeats its value for agents earlier than 2.0.0, which read that field, and is removed with the next protocol generation. `target_version` is the latest version published on the server's channel (`Server.channel`, `stable` by default; a `beta` server also sees `stable` versions) for its architecture, never older than the one it already targets or runs — except when that version has been withdrawn from the channel by a promotion: the target then falls back to the channel's latest current version, which is the path of the rollback. `minimum_version` is the floor the platform retains for this server: the last agent version it has seen it run, `null` as long as it has seen none. A `suspended` server — by licence or by the team — receives `authorized_keys: []` and `keys: []`. `keys[]` is `AgentStateKey` (`@pupitre/shared/keys`): `{ public_key, user_id, device_id, approvals[] }`, one entry per device key the server must carry, `public_key` as `type base64` without a comment, with each `KeyApproval` kept for this server and this device, `issued_at` as it was signed; this is what an agent of this version reads, which ignores `authorized_keys`, kept for older agents. See [approved keys](./agent-protocol.md#a-key-only-enters-on-an-approval). The row is written only when the target changes or the licence horizon has moved by more than an hour: a poll every thirty seconds does not cost a write |
| POST | `/agent/heartbeat` | `{ disk, ram, load, sessions[], stack_version, modules[], agent_version?, ssh_user?, disk_total_gb?, disk_free_gb?, ram_total_mb?, ram_used_mb?, backup?, keys? }` | 204. `keys` is `KeysBeat` — `{ signers[], pending[] }`, `SHA256:` fingerprints only, a hundred at most each — kept with its date in `Server.keyReport`; an agent that omits it leaves the known value. The sample joins `Server.metrics`, a sliding 7-day window, and its summary without lists replaces `Server.lastUsage`. `ssh_user` is the account whose `authorized_keys` block the agent holds — `dev` once the machine is hardened — and replaces `Server.sshUser`: this is the account `GET /me/servers` gives each device, where the enrolment had seen only that of the installation. An agent that omits it leaves the known value; an `ssh_user` that is not a POSIX account name (`isSshUser` from `@pupitre/shared/ssh`) returns `validation` (422) without writing anything. `sessions` and `modules` carry at most 100 names of 200 characters; beyond that, `validation` (422) |
| GET | `/agent/release/:version` | — | 303 to a signed R2 URL, valid for 5 minutes, for the server's architecture. `release_not_found` (404) if the version does not exist for this architecture |
| GET | `/agent/release/:version/metadata` | — | `{ version, arch, sha256, signature, channel }` for the server's architecture: the expected fingerprint and the Ed25519 signature of this version, as the release chain deposited them. `release_not_found` (404) if the version does not exist for this architecture |

The agent reads the metadata before downloading: it takes the fingerprint and the signature from there instead of receiving them from the app, and the floor from `/agent/state` tells it whether it is allowed to install this version. A refusal then costs one call, not a binary.

`stack_version` carries the version of the agent itself, the same value as `agent_version`. The name comes from the original bash stack, where the two differed; there is now only one binary.

Revoking a device (`DELETE /me/devices/:id`, `POST /servers/:id/revoke-device`) leaves the platform only at the server's next **successful** read of `/agent/state`: a `stale` machine keeps the key as long as it does not answer, and the console says so. The agent never removes the last key of its block: a revocation that would leave none removes nothing.

`disk` and `ram` are percentages; the four optional fields carry the quantities the machine has actually measured, the only ones able to say "1.8 GB of 556 GB". They are optional because an earlier agent does not send them: the console then falls back on the percentage alone, and a server that has not been updated yet does not display zero bytes. `usage` and `metrics` return them as they are, as `null` when the sample did not carry them.

| Method | Route | Auth | Response |
| --- | --- | --- | --- |
| GET | `/releases/agent/:version?arch=` | device bearer | 303 to a signed R2 URL, valid for 5 minutes: the app downloads the agent binary to push it itself onto the server. `arch` is `amd64` by default |

### Desktop app releases

| Method | Route | Auth | Response |
| --- | --- | --- | --- |
| GET | `/releases/app?channel=stable&limit=10` | none | `{ data: AppRelease[] }`, from the most recent to the oldest: what the site's download page reads at build, then again from each visitor's browser. Empty list, never 404 |
| GET | `/releases/app/latest?channel=stable` | none | `{ data: AppRelease }`: the highest version of the channel, its notes and a `build` per published artifact. `channel` is `stable` by default; a `beta` channel also sees `stable` versions. `app_release_not_found` (404) as long as nothing is published — the console then says there is nothing to download rather than display a dead link |
| GET | `/releases/app/:version` | none | `{ data: AppRelease }` for a specific version, whatever its channel; `app_release_not_found` (404) otherwise |
| GET | `/releases/app/:version/:os/:arch` | none | 303 to the artifact, the stable link that the site and the help pages write; `app_release_not_found` (404) for an architecture nobody has built |

`AppRelease` is `{ version, channel, notes, published_at, builds: [{ os, arch, format, url, bytes, sha256, signature }] }`, one `builds` entry per downloadable file. The `url` returned here is **composed by the platform** from the stored key and `PUPITRE_DOWNLOADS_URL`: publication sends only a key (`r2_key`), reading returns an address — two on macOS, one per architecture. `arch` is `arm64`, `x64` or `universal`: Electron's vocabulary, which is not that of the agent's catalogue (`amd64`, `arm64`). The notes belong to the version: the row published first carries them for the whole version.

These four routes require no session, unlike those of the agent: the app's artifacts are public — they live on `dl.pupitre.studio` — whereas the agent's binary is not.

Being open to everyone, they answer `access-control-allow-origin: *` and `cache-control: public, max-age=300` — the site reads them from the browser, on another origin than the console — and carry a rate limit of their own: 60 requests per minute per `cf-connecting-ip` (`PUBLIC_RELEASES_RATE_LIMIT`), above which they return `rate_limited` (429) with `retry-after`. This budget is distinct from the global budget: an address that hammers the version list does not consume the one it needs for the console. These two headers apply only to these four routes: the hook that sets them is **local** to the router, and not `scoped`, otherwise it would reach every route mounted after it — the `/admin` routes and the Stripe webhook included.

### Affiliate link visit counter

| Method | Route | Auth | Response |
| --- | --- | --- | --- |
| POST | `/affiliate/:code/hit` | none | 204, empty body. The **enabled** link that carries this code gains one visit on the current day, in universal time: an `upsert` on `(linkId, day)`, nothing else. The response is 204 whatever the code — unknown, disabled or malformed — so that a caller learns nothing about the links the platform holds. `rate_limited` (429) with `retry-after` beyond 60 requests per minute per `cf-connecting-ip` (`AFFILIATE_HIT_RATE_LIMIT`), a budget distinct from the global budget. The call comes from a `navigator.sendBeacon` of the site, hence from the `connect-src` of the site's security policy: `PUPITRE_ORIGINS.app` is in `apps/site/public/_headers`, without which the browser refuses the beacon and the counter stays at zero; a site test (`apps/site/scripts/headers.test.ts`) guards the rule |

The site's affiliate script calls it with `navigator.sendBeacon`, once per session and per code, right after setting the `pupitre_ref` cookie: empty body and no header of its own, hence a simple request, without a preliminary `OPTIONS`. The route answers `access-control-allow-origin` to the site's origin (`PUPITRE_ORIGINS.site`) and, when the console runs locally, to a local origin; any other origin receives the response without a CORS header, and the browser discards it. **What the platform keeps of a visit is a counter per link and per day, and nothing else**: no IP address, no third-party cookie, no identifier, no landing path — two visitors on the same day are indistinguishable.

### Platform

All these routes live under `/admin/**` and stay out of the OpenAPI document (`hiddenRoutes`). The **Role** column says which of the two guards protects them: **member** for a read (`requirePlatformAdmin`, any member of the Pupitre organization), **admin** for an action (`requirePlatformRole("admin")`, `owner` or `admin` of that organization), **publication** for the four version routes.

The **publication** role opens the four version routes to two callers, and to them alone:

- **The release pipeline**, which presents the `PUPITRE_PUBLISH_TOKEN` token as `Authorization: Bearer`. The token carries the `pupitre_pub_` prefix, by which the platform tells it from a session; it is declared on the Worker and in GitHub Actions, compared on SHA-256 fingerprints, and opens nothing else. `PUPITRE_PUBLISH_TOKEN_PREVIOUS` is accepted at the same time, for the duration of a rotation. A refused token returns `unauthenticated` (401).
- **An `owner` or an `admin` of the Pupitre organization**, with their session, so that a version remains promotable by hand from the console. A plain member is refused there as on the other actions, with `platform_role_required`.

The audit log keeps the two apart: a pipeline publication has no `actorUserId` and carries `by: "pipeline"` in its payload.

### Backups

The platform knows that a backup exists, where it is, and how much it weighs; it knows nothing of what it contains. The full contract is [backups.md](./backups.md), the `BackupDeclaration` and `BackupBeat` shapes are in `@pupitre/shared/backup`.

| Method | Route | Auth | Response |
| --- | --- | --- | --- |
| POST | `/agent/backups` | server token | `BackupDeclaration` body: `{ id, created_at, trigger, name?, bytes, counts: { setup, home, databases, projects, paths }, config_revision, agent_version, recipient, kdf_salt, location: { endpoint, region, bucket, key, path_style, sha256 } }`. Response `{ data: Backup }`: 201 on creation, 200 if this server has already declared this identifier (the daemon redeclares what an outage left pending), `conflict` (409, `backup_id_taken`) if another server of the organization holds it. Writes `backup.created` |
| DELETE | `/agent/backups/:id` | server token | 204. Removes the reference of a backup **of this server**, once its objects have been erased from the bucket — by pruning or by `backup.delete`. `not_found` (404) for another server's identifier. Writes `backup.deleted` |
| GET | `/backups` | session, active organization | `{ data: Backup[] }`, most recent first; a forgotten reference no longer exists, those of removed servers remain. A `member` sees only the backups of the servers assigned to them; `admin` and `owner` see everything |
| GET | `/servers/:id/backups` | session | `{ data: Backup[] }` of a server, same rules; `not_found` (404) for a server the caller cannot see |

`Backup` returns `{ id, server_id, server_name, created_at, trigger, name?, bytes, counts, config_revision, agent_version, recipient, kdf_salt, location }`; `server_id` is `null` once the server's row is erased, `server_name` remains.

`/agent/state` additionally returns `server_id`, which the agent keeps in `/etc/pupitre/server.id` and which names its prefix in the bucket. `/agent/heartbeat` additionally accepts `backup: BackupBeat` — `{ interval_hours, last_run_at?, last_ok_at?, last_error?, last_warnings? }` —, kept in `Server.backup`; an agent that omits it leaves the known value, an agent without a backup module does not send it. `GET /servers` and `GET /servers/:id` return `backup` as is, or `null`.

`EvaluateAlerts` opens `backup_failed` when `last_error` is set and `last_run_at` is more recent than `last_ok_at`, or when `last_warnings` is positive — the last backup exists but is missing parts, and the email says so under its own title, with their number —, and `backup_stale` when `interval_hours` is positive and `last_ok_at` is more than two intervals old (`backupStaleAfterHours`). Same mechanics as the other alerts: one open row per kind and per server, an email to the owners, closure on return to normal.

Details held by the code:

- The declaration's `created_at` and the beat's `last_run_at`, `last_ok_at` are ISO 8601 dates (`format: date-time`): the platform stores and compares them. `location` accepts no field beyond the six of the contract (`additionalProperties: false`, like `z.strictObject`): an access key slipped in there is refused with `validation` (422). `bytes` is kept as `BIGINT` and returned as a number.
- The two alerts target only an `active` or `grace` server, like the others: a suspended server does not back up. `backup_failed` also holds a server that has never succeeded (`last_ok_at` absent); `backup_stale`, on the contrary, requires a first success — without it, there is no lateness to measure, and the failure is reported by `backup_failed`.
- A `member`'s visibility follows the server's current assignment: the backup of a removed server (null `server_id`) is visible only to an `admin` or an `owner`. `POST /backups/:id/forget` and `POST /backups/:id/restored` return `not_found` (404) for a reference already forgotten, since it is erased.
- `backup.created` and `backup.deleted` have no actor (the server acts) and carry `{ server_id, server_name }` (plus `trigger` and `bytes` on creation); `backup.forgotten` carries the backup's `{ server_id, server_name }`; `backup.restored` carries the restored server's `{ server_id, server_name }` and the `{ from_server_id, from_server_name }` of the one that had made it. All have the organization and `target_id` = the backup's identifier.

### Webhooks

| Route | Events |
| --- | --- |
| POST `/webhooks/stripe` | In `off` mode, `conflict` (409, `billing_off`) without reading anything: no Stripe event is expected. In `stripe` mode: `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`. No session guard: the `t=…,v1=…` signature is verified as HMAC-SHA256 over the raw body, with a five-minute tolerance. The `StripeEvent` row keeps the subscription the envelope names (`subscriptionId`), which the console's subscription record reads. An invoice's subscription is read from the same place for the whole webhook: `subscription`, then `parent.subscription_details.subscription` (the Stripe 2025 API shape), then `parent.subscription`. Idempotent by `event.id`: the `StripeEvent` row is **claimed before any processing** — two concurrent deliveries collide on the primary key and only one processes —, then marked `processed`; a processing that throws leaves the row `failed` and answers 500, which asks Stripe to replay, and that replay takes the row up again. A row left `processing` beyond the lease (`STRIPE_EVENT_LEASE_MINUTES`, five minutes by default, read from `receivedAt`) — a dead isolate, or a `failed` marking that itself threw — is taken up in the same way; as long as another delivery holds it within its lease, the answer is 409 `conflict` `stripe_event_in_flight`, so that Stripe replays. Only a `processed` row answers 200 `duplicate: true`. Each event, `invoice.payment_failed` included, reads the subscription again at Stripe and copies what Stripe says about it: a late delivery does not resurrect a cancelled subscription and does not overwrite a more recent state; an invoice without a subscription is not processed. Response `{ received, handled, duplicate }`; signature absent, invalid or out of tolerance: `stripe_signature_invalid` (400) |

On every `customer.subscription.*`, the platform **reads the subscription again at Stripe** before believing it: the event that arrives last is not always the one that happened last, and a late `updated` does not resurrect a cancelled subscription. After each event, the servers follow the licence that counts (that of `/me`): `active` or `trialing` brings back to `active` the `grace` servers and those that billing had suspended (`suspendedReason: billing`), never those the team suspended; `past_due` and `unpaid` — `invoice.payment_failed` included — open a seven-day grace period on `active` servers, and on them alone: a server already in grace keeps its date, whatever Stripe's retries, and the `license_grace` email goes out only if there was something to switch; `canceled` opens the grace period until the end of the paid period, except for an organization that fits within its free servers. `SuspendExpiredGrace` then suspends, noting `billing`. `/agent/state` reads this licence.

### Billing mode

`BILLING_MODE` (`off` by default and in production, `stripe`) is read by `packages/api/src/lib/billing/config.ts` and carried by the runtime (`configureBilling({ mode })`), which the tests set without touching the environment; it lives in `vars` of `apps/web/wrangler.jsonc`. **In `off`**, the platform sells nothing and never calls Stripe: checkout, seats, portal and webhook refuse with `conflict` (`billing_off`), the admin actions that would go through Stripe with `conflict` (`billing_off_stripe`), and no Stripe key needs to exist. **In `stripe`**, the earlier code goes back into service to sell licences beyond the free servers ([decision 0007](../decisions/0007-stripe-managed-payments.md), amended by [0018](../decisions/0018-source-available-and-free.md)). `STRIPE_DASHBOARD_URL` (optional) says where the team reads a subscription at Stripe; without it, `dashboard.stripe.com`, prefixed with `/test` when `STRIPE_SECRET_KEY` is a test key — no Stripe address is written in a component. **The Pupitre organization** (`PLATFORM_ORGANIZATION_ID`) needs no licence: its own is `valid` by what it is (`licenseForOrganization`), and its seat quota is `PLATFORM_ORGANIZATION_SEATS` whatever the mode (`seatQuotaFor`, source `platform`). The affiliate links serve only to trace where sign-ups come from and how many servers they enrol.

**What the team changes at Stripe.** Taking back a cancellation that was waiting for the end of the period (`POST /admin/subscriptions/:id/resume`) is a **Stripe-first** action: the platform sets `cancel_at_period_end: false` at Stripe, then the mirror takes what Stripe answers, exactly like `POST /admin/subscriptions/:id/cancel`. The webhook that follows then finds the row identical and changes nothing: this is what makes the double path idempotent. In `off` mode, these actions refuse with `conflict` (`billing_off_stripe`). The mirror's `cancelAtPeriodEnd` is written only by this path and by the webhook; no task deduces it.

**The granted licence.** In both modes, the team can grant a licence from the console (`POST /admin/organizations/:id/subscriptions`): a separate product, `granted` (`GRANTED_PRODUCT`), with the seats and the deadline it chooses, `active` from the grant, without Stripe; it is today the only way to exceed `FREE_SERVERS`. `granted` forms `PLATFORM_PRODUCTS` (`@pupitre/shared/plans`, `isPlatformProduct`): the product with no Stripe counterpart, which `ReconcileSeats` ignores, which `POST /orgs/:id/seats` refuses (`seats_locked`) and for which `POST /orgs/:id/portal` has nothing to open (`billing_granted`). The app sees only `license`, `servers` and `license_grant` of `/me`. A grant with a deadline expires through the daily task: `expireGrantedSubscriptions` turns to `canceled` every `active` `granted` whose end has passed, with a `subscription.canceled` event, and its servers take that date as grace when that grant is the one that counts and the organization holds more than its free servers.

**`fromContract`** (`packages/api/src/lib/api/contract-schema.ts`) derives from a zod schema the TypeBox that Elysia validates: zod → JSON Schema → `t.Object`, `t.String`, `t.UnionEnum`… The API thus keeps its translated validation messages, which read TypeBox's errors, its normalisation (`normalize: "typebox"`, for lack of AOT on Workers) and its OpenAPI document, without redeclaring a shape. A test (`contract-schema.test.ts`) passes the same values to both and requires the same verdict. A shape that JSON Schema does not render in TypeBox (a record, a reference) is refused at startup, not tolerated.

**A response the app cannot read is a refusal**, `refusal.platform.unreadable` with the path called, never a guessed value. The consequence is a commitment of the platform: **adding a value to an enumeration in a response, making a new field required or removing one, breaks the apps published before**; such a change waits until those apps are below the floor, or is done through a new, optional field.

The dates of these shapes follow `InstantSchema`: RFC 3339, with `Z` or an offset. The platform validates them on the way in as on the way out, which `format: date-time` alone did not do for `BackupDeclaration.created_at` and `BackupBeat.last_*_at` on the app and agent side.

## Long-running tasks

Cloudflare Workflows in `apps/web/src/workflows/`: `ReconcileSeats` (daily: the licence's seats against the servers that occupy a seat beyond `FREE_SERVERS`; it never touches Stripe, but an organization that occupies more seats than its quota receives a `seats.drifted` event in its log and the `seats_drift` email to its owners — once per drift, again only when the paid or occupied seats change), `DecommissionServer` (seven days after deletion or non-payment; a server's metric samples go in batches before it), `ExpireEnrollments` (enrolment tokens not exchanged within an hour), `EvaluateAlerts` (every hour: `evaluateAlertsBatch()` of `packages/api/src/lib/alerts/alerts.ts`, then the emails in steps of their own; an alert still open whose email did not go out is retried at the next pass), `PurgeDeletions` (daily, in order: `purgeDeletedOrganizations()` then `purgeDeletedUsers()` of `packages/api/src/lib/platform/purge.ts`, one step per batch, then the retention sweeps of `packages/api/src/lib/platform/retention.ts`), `SuspendExpiredGrace` (daily, in order: the grants' expiry of `packages/api/src/lib/billing/admin.ts`, the suspension of `packages/api/src/lib/billing/grace.ts`, then each organization's suspension email in a step of its own). Each workflow advances in bounded batches, one step per batch: D1 binds only about a hundred values per query, and a replay resumes only the batch that failed. A cron starts each instance under the identifier `<workflow>-<scheduledTime>`, so a wake-up delivered twice launches nothing twice, and a workflow that refuses to start does not prevent the others. The grants' expiry turns to `canceled` every `active` `granted` licence whose end has passed (`cancelEndedSubscriptions` of `packages/api/src/lib/billing/expiry.ts`), with a `subscription.canceled` event. The organization's servers go into grace until that end, already past, only if no other licence in progress covers it **and** the organization holds more than `FREE_SERVERS`: an organization that falls back within its free servers keeps its machines active. The grace is set before the cancellation, so that a batch replayed after an outage finds its rows instead of leaving servers running on a dead licence. Where the grace period opens, the suspension step that follows closes them the same day, noting `billing`.

`PurgeDeletions` erases what the seven-day grace period let through: first the organizations whose `deletionAt` has passed, through `purgeOrganization` — their log, then the cascades —, then the accounts whose `deletionAt` has passed, through `purgeUser` — the organizations of which they were the last member, what the log says about them and their devices, their device codes, then the cascades. The organizations go first so that an account erased in the same pass is no longer the last owner of anything. Each erasure writes `organization.purged` or `user.purged` with a null actor, since it is the task that acts, and without payload. An account that became, during its grace period, the only owner of an organization that still carries a seat-occupying server or a subscription in progress is **not** erased: it is skipped, and a `user.purge_skipped` `{ reason: "sole_owner", organization_id }` event is written only at the first skip, then again only when the organization that holds it changes or its deletion is rescheduled. Idempotent, in batches of twenty-five, one step per batch up to the last: the organizations until an incomplete batch, the accounts by increasing identifier, so a skipped account never clogs the queue of the others.

Then four retention sweeps, each in passes of 50 batches of 90 rows (D1 binds at most a hundred values per query), one step per pass until an incomplete pass: the `ServerMetric`s older than seven days (`METRICS_WINDOW_MS`, through the index on `at`), which a silent server no longer prunes itself at its heartbeat; the sessions, verifications and device codes whose `expiresAt` has passed.

Two Cron Triggers start them, `apps/web/src/workflows/registry.ts` says which: every hour the expiry of enrolments and the evaluation of alerts, every day at 3:20 the decommissioning, the seat reconciliation, the suspension of elapsed grace periods and the purge of scheduled deletions. Two wake-ups and not five: the database sleeps between two passes instead of being woken every quarter of an hour — a server is said to be unreachable after thirty minutes without a beat, and an alert an hour later is the same alert. An internal route protected by a shared secret allows triggering them on demand.
